## 1. Что это

Отдельная вкладка в корпоративном Task Tracker AVANT: реестр регулярных и разовых **IT / интернет-оплат** (хостинг, домены, CRM, плагины, связь, реклама, AI-сервисы).

Это **не** бухгалтерия, **не** 1С, **не** учёт зарплат и **не** синхронизация с Google-таблицей в реальном времени.

Это операционный реестр: *что платить, когда, чем, кто платит, кто отвечает за сервис* — чтобы не пропустить дату, вовремя поставить задачу и видеть ближайшие платежи без Excel.

Название в UI:

| Локаль | Пункт меню |
|--------|------------|
| ru | Оплаты |
| uk | Оплати |
| en | Billing |

URL (предложение): `/billing`, карточка `/billing/{id}`.

## 2. Зачем

Сейчас учёт размазан по книге Excel/Google Sheets «ИT затраты и инет платежи»:

- один лист — счета ТОВ на бухгалтерию (грн, договоры, «по счету»);
- другой — WordPress-плагины в USD/EUR;
- третий — операционный список сервисов;
- четвёртый/пятый — **помесячная копия** тех же строк на 2025–2026 с пометкой Card pay.

Из-за копирования месяцев данные уже разъехались (Cursor и Adobe Firefly в осенних блоках с датой августа; Vimeo Advanced 1080 USD на листе «Сервисы» vs 780 USD в бюджете марта). Напоминаний нет. Задачу «пойти оплатить» никто не ставит автоматически. Карта и расчётный счёт живут в разных вкладках.

Модуль должен:

1. Показать **важное в списке**, без открытия карточки (как задачи).
2. Свести разные виды оплат к **одной модели**.
3. Хранить способ: наличные / карта / расчётный счёт; для карты — **только последние 4 цифры**.
4. Считать ближайшую дату, слать уведомление за **7 и 3 дня**, за 7 дней создавать **задачу на ответственного за оплату**.
5. Различать **кто платит** и **кто отвечает за сервис**.
6. Показывать вкладку **только тем, кому доступ выдал админ**.

## 4. Что увидели в таблице: виды оплат

Один список в продукте должен покрыть все эти режимы. **Не копировать 12 месячных блоков** из Card pay — это проекция, не реестр.

| Вид | Пример из таблицы | Как моделировать |
|-----|-------------------|------------------|
| Подписка с календарной датой | Kommo 02.06.2026, LearnDash 14.01.2026 | `kind=subscription`, `period_months=1\|12`, `next_due_on` = дата |
| День каждого месяца | HeyGen «3 числа», UA-Hosting «до 10 числа», ChatGPT «29 авг.» | то же + `due_day_of_month` и правило «до N-го» (§6.5) |
| Год, дата начала/продления | Crocoblock 20.08.2026, Box 23.09.2026 | `kind=subscription`, `period_months=12` |
| Сумма «по счету» | Київстар, Інтертелеком | `amount` пуст — этого достаточно, отдельного флага не заводим |
| По необходимости | HeyGen доп. кредиты, OpenAI, EdenAI | `kind=on_demand`, крона нет, пока не проставят дату |
| Ежедневные списания / бюджет | Google Ads, FB/Inst | `kind=ad_budget`, `period_months=1`, **не** ежедневные задачи |
| Lifetime | User Role Pro, Filebird | `kind=lifetime`, без даты и напоминаний |
| Автопродление карты | ChatGPT Plus | флаг `auto_renew`, напоминание «проверить списание» |
| Разовое | пополнение API, Hostinger 990 USD в ноя 2025 | `kind=once` |
| Безнал / бухгалтерия | весь лист «Интернет, хостинги, телефония» | `method=bank` |
| Карта | лист «2026 Card pay» | `method=card` + last4 |
| Наличные | в таблице нет, запрошено владельцем | `method=cash` |

Валюты в ячейках: грн / UAH, USD (опечатки `uds`, `EURO`/`eu`/`EUR`). Нормализовать: `UAH`, `USD`, `EUR`.

## 6. Продуктовая модель

### 6.1. Доступ

Два новых permission (имена рабочие):

| Permission | Смысл |
|------------|--------|
| `view_billing` | Видеть пункт меню, список, карточку |
| `manage_billing` | CRUD, «Оплачено», пауза |

Админ (`system_type=admin`) видит всё как сейчас. Остальным — роль в `/admin/roles` (например роль «Оплаты»). Без права: пункта в nav нет, middleware режет `/billing*`.

Владелец сервиса **не обязан** иметь вкладку. Ему достаточно автозадачи.

**Отделов в биллинге нет** (решение 2026-08-27). Правило Task Tracker «создавать и редактировать может только человек из того же отдела» относится к задачам и на оплаты **не распространяется**: у `billing_items` нет `department_id`, доступ определяют только `view_billing` / `manage_billing`. Бухгалтер из Финансового отдела заводит и правит строку по хостингу, которым занимается IT, — и это нормально.

Отдел появляется ровно в одном месте — у **порождённой задачи**, потому что этого требует `TaskService` (§3.2). Берётся из отдела `payer`. Следствие, которое надо обработать: у пользователя `department_id` nullable, а `resolveAssignee()` отклоняет неактивного исполнителя. Если у payer нет отдела или он деактивирован — задачу создать не на что: не падать молча, а показать строку в списке как «Не могу поставить задачу: у плательщика не указан отдел» и уведомить админа.

Кандидаты на первый доступ (не назначать без апрува Максима): Максим; Зинаида; Ирина Викторовна. **Решение по умолчанию (§7 п.5): на старте право получает только Максим**, остальные — когда он скажет.

### 6.3. Список (как задачи)

Каркас как `tasks/index`: белая таблица `rounded-xl`, поиск, фильтры, сортировка, empty state, md-таблица / mobile-карточки.

Табы:

- Просрочено  
- Ближайшие 7 дней  
- Все активные  
- По необходимости  
- Навсегда  
- На паузе  
- Архив (больше не платим) — отдельный таб, в сводку и крон не попадает  

В строке без карточки:

1. Поставщик · продукт  
2. Категория (короткий badge)  
3. Сумма + валюта **или** «по счету»  
4. Следующая дата (красный просрочено, янтарный ≤7 дней — как `deadlineMeta` у задач)  
5. Способ: `Нал` / `Карта •••• 1234` / `Счёт`  
6. Платит · сервис (оба имени, если разные)  
7. Статус — **производное**, отдельного хранимого поля у сервиса нет: `Просрочено` / `Скоро` (≤7 дней) / `Активен` / `Пауза` / `Навсегда` / `Нужен ответственный` (пустой `payer_user_id`). Факт оплаты живёт в `billing_payments`, а не в поле статуса  
8. Кнопки **Оплачено** и **Отменить оплату** (`@click.stop`, без перехода в карточку) — сценарий подтверждения в §6.7 п.3, правила в §6.5

Сводка сверху: сумма к оплате в текущем календарном месяце по валютам (замена «Загальний бюджет за січень»). Суммы **не складываются между валютами** (курса в v1 нет, §6.8). Отдельно строкой: «+ N позиций по счёту» (`amount` пуст — Київстар, Інтертелеком) и «+ N рекламных бюджетов» (`ad_budget` со щоденними списаннями) — они в сумму не входят, иначе цифра врёт.

Фильтры: способ, плательщик, владелец, категория, валюта, период.

Сортировка по умолчанию: просроченные, затем ближайшая дата.

### 6.4. Карточка

Форма + история оплат + ссылка на открытую задачу. Редактирование — страница или боковая панель в том же визуальном языке, что задачи (не новая дизайн-система). **Создание** идёт через мастер в 4 шага (§6.7 п.4), а не через ту же полную форму; в карточке полная форма остаётся для правок, включая дату платежа, которую подтверждение «Оплачено» не спрашивает.

### 6.5. Напоминания и задачи

Отдельная команда, например `billing:send-reminders`, в scheduler **раз в сутки в 09:00 Europe/Kyiv** (`->dailyAt('09:00')`), не каждые 30 минут и не «когда придёт `schedule:run`».

`next_due_on` — **всегда материализованное поле**, вся логика крона смотрит только на него. Для строк с `due_day_of_month` («3 числа», «до 10-го») дату вычисляет тот же крон. Вычислять «на лету» в запросах нельзя — иначе фильтры, сортировка и сводка расходятся с уведомлениями.

Два правила материализации:

- **`due_day_of_month = 29, 30, 31`** в коротком месяце — clamp на последний день месяца (29 февраля не выдумывать, взять 28-е).
- **`due_day_rule = until` («до 10-го»)** — `next_due_on` = N-е число, напоминание за 7 дней как обычно (для «до 10-го» это 3-е), но **не раньше 1-го числа месяца due**: иначе для «до 5-го» напоминание уезжало бы в предыдущий месяц и читалось бы как чужой платёж.

| Момент | Действие |
|--------|----------|
| −7 дней до `next_due_on` | Уведомление payer + owner (если разные). Создать **одну** задачу на payer |
| −3 дня | Только уведомление |
| День оплаты и дальше, пока не «оплачено» | Уведомление payer + owner о сроке/просрочке (те же получатели, что и на −7); задачу не дублировать |

Автозадача:

- title: `Оплатить {vendor} {product} до {date} — {amount} {currency}`  
- assignee = payer  
- department = отдел payer (инвариант Task Tracker; на сам биллинг отделы не влияют — см. §6.1). Если отдел у payer пуст или payer неактивен — задача не создаётся, строка помечается ошибкой  
- initiator = **отдельный технический пользователь «Оплаты»** (решение 2026-08-27): `system_type=admin`, без Telegram и без email-уведомлений. Его `isAdmin()` снимает и `Gate::authorize('create')`, и проверку отдела инициатора в `TaskService` (проверено по коду, §3.2) — отдельный «обход Gate» писать не нужно. Живого человека инициатором не ставим: иначе все ~50 задач в год числятся за Максимом, ему идут уведомления инициатора и к нему возвращаются задачи с `on_review`  
- watchers = `owner_user_id`, если это другой человек. Отдел наблюдателем быть не может — `owner_label` в задачу не идёт  
- priority = **7** (шкала 1–10, дефолт 5, сортировка по убыванию — проверено по коду). Пропущенная оплата = простой сервиса, она должна лежать выше обычной задачи  
- deadline = дата оплаты  
- category = **Оплаты** (создать в каталоге)  
- описание: способ, last4, ссылка `/billing/{id}`, договор/л/с  

Идемпотентность: для пары `(billing_item_id, next_due_on)` не больше одной открытой задачи.

**Guard первого прогона:** крон не создаёт задачи за уже прошедшие циклы — при первом запуске после импорта фиксирует `reminder_*_sent_for` текущим циклом, задачи начинаются со следующего.

Порядок важен: сначала импорт по §6.6 п.5 ставит всем строкам **будущий** `next_due_on`, только потом включается крон. При таком порядке guard почти не срабатывает — он остаётся страховкой для строк, заведённых руками с прошлой датой, и для случая, когда крон не работал неделю.

#### Две кнопки: «Оплачено» и «Отменить оплату»

Обе доступны **и в списке `/billing`, и прямо в задаче** — человек живёт в задачах, во вкладку он может не ходить.

**Кто может нажать** (решение 2026-08-27): держатель `manage_billing` — по любой строке; `payer` — по **своей** строке из **своей** задачи, даже без `view_billing`. Ничего другого в биллинге он при этом не видит.

**«Оплачено»:**

1. Запись в `billing_payments` (`type=paid`): дата = сегодня, сумма, способ, кто отметил, `task_id`.
2. Сдвиг `next_due_on` по правилу цикла (ниже).
3. Комментарий в связанную задачу и перевод её в `completed`.
4. Сумму в этот момент можно поправить — реклама и «по счету» приходят фактом.

**«Отменить оплату»** — решили в этом цикле не платить (сервис не нужен, счёт не пришёл, перенесли):

1. Запись в `billing_payments` (`type=skipped`) с **обязательной причиной** — иначе пропуск платежа теряется бесследно.
2. Сдвиг `next_due_on` на следующий цикл по тому же правилу. Строка не остаётся в вечной просрочке.
3. Задача переводится в `cancelled` с той же причиной в комментарии.
4. Если платить больше не собираемся — это не «отменить», а «Больше не платим» (`state=archived`, §6.7 п.8). Разные кнопки, разный смысл.

**Правило цикла — одно на импорт и на обе кнопки.** `next_due_on` увеличивается на `period_months`, пока не станет **строго больше сегодняшней даты** (Europe/Kyiv). Не «+1 период от due» и не «от сегодня»:

- заплатили заранее → дата уезжает ровно на один цикл, как и ожидается;
- заплатили с опозданием (due 10 июня, факт 20 августа) → цикл прокручивается до 10 сентября, а не до 10 июля, которое снова в прошлом и мгновенно даёт новую просрочку;
- годовая строка (LearnDash, due 14 января, оплатили в августе) → 14 января **следующего** года.

**Что происходит после кнопки, по видам:**

| kind | «Оплачено» | «Отменить оплату» |
|------|-----------|-------------------|
| `subscription` | сдвиг `next_due_on` по правилу цикла | сдвиг на следующий цикл, задача `cancelled` |
| `ad_budget` | сдвиг на месяц (одна проверка в месяц, не 30) | сдвиг на месяц |
| `once` | платёж записан, `next_due_on` очищается, строка предлагает «Больше не платим» — **но не архивируется сама** | дата **не очищается** — тот же цикл вперёд, что у подписки (иначе строка без даты ломает валидацию). Если платить больше не будем — «Больше не платим» |
| `on_demand` | платёж записан, даты не было и не появляется | кнопки нет — без даты нечего отменять |
| `lifetime` | кнопок нет вовсе | — |

**Источник правды — только `billing_payments`.** Из этого следуют три правила, иначе появятся два учёта и крон начнёт врать:

- ручной перевод задачи в `completed` (без кнопки) **не** создаёт платёж и **не** двигает `next_due_on` — крон продолжит считать строку неоплаченной, и это правильно;
- если оплату отметили, когда задача уже `completed` / `cancelled` / `rejected` — платёж записывается, в задачу идёт комментарий, **статус задачи не трогаем** и не переоткрываем;
- у пары `(billing_item_id, next_due_on)` может быть максимум одна запись `paid` — повторный клик показывает «уже отмечено», а не плодит платежи.

Не создаём задачи: `kind=lifetime`, `kind=on_demand` без даты, `state` не равен `active`, а также строки с пустым `payer_user_id` (их видно в списке как «нужен ответственный»).

Для `ad_budget` задача **создаётся**, но одна в месяц — «проверить рекламный бюджет», не 30 штук по числу щоденних списань.

Групповой Telegram задач не трогаем. События `billing.due_7`, `billing.due_3`, `billing.overdue` — в preferences профиля (как task.*).

### 6.6. Заливка данных

Разовая, не sync с Google.

1. Уникальные строки из «Сервисы» + «Плагины» + «Интернет…».  
2. Card pay 2026 — только подсказка `next_due` и `method=card`.  
3. Бюджет 2025 — подсказка рекламы и статусов, не мастер.  
4. Конфликты — **не угадывать**, спросить Максима при заливке. Полный список в §5.4.
5. **Пересчёт дат вперёд.** Дата из таблицы — это дата *последнего известного* платежа, а не следующего: больше половины строк §5 уже в прошлом (Ringostat 12.09.2025, WooNinjas 22.11.2025, Easy WP SMTP 16.12.2025, LearnDash 14.01.2026, Crocoblock и Elementor 20.08.2026). При импорте `next_due_on` = дата из таблицы, прокрученная вперёд по тому же правилу цикла, что и кнопка «Оплачено» (§6.5): `+= period_months`, пока не станет строго больше сегодняшней. Исходную дату сохранить в `notes` — чтобы было видно, откуда посчитали.
6. Нормализация: валюты `UAH / USD / EUR` (из `грн`, `uds`, `EURO`, `eu`), десятичная запятая → точка, пробелы в тысячах убрать.
7. Строки без ответственного (EdenAI, OpenAI, ChatGPT, реклама 2025) заливаем с пустым `payer_user_id` — в списке они видны как «нужен ответственный» и не порождают задач, пока Максим не проставит человека.
8. `owner_user_id` из колонки «Відділ / Ініціатор»: отдел мапится на руководителя (`Department.head_user_id`), исходный текст сохраняем в `owner_label`. «Учебный отдел» → Коханский; «IT» → руководитель IT. Имя человека («Ірина» = HeyGen) сначала сверить по `list_users` — в §3.3 есть предупреждение не спутать Назарову Ирину с Ириной Викторовной.
9. Парсер писать **отдельный, под CSV листов §3.1**. `ExcelTaskImportService` для этого не годится: он читает лист «Лист задач» из `IT-Task-Tracker.xlsx` и создаёт `Task` (проверено по коду). Переиспользуем только **подход**: `dryRun`, отчёт `imported / skipped / preview` с причинами, маппинг колонок отдельными методами.

### 6.7. UX для неподготовленного пользователя

Модулем будут пользоваться бухгалтерия и учебный отдел, а не разработчики. Решения ниже **апрувнуты 2026-08-27** и входят в v1 наравне с функционалом — это не «полировка потом».

**1. В интерфейсе нет жаргона.** `on_demand`, `ad_budget`, `lifetime`, `period_months` остаются в БД и коде, наружу идут фразы: «Каждый месяц», «Раз в год», «Когда закончатся деньги», «Реклама — списывается ежедневно», «Куплено навсегда», «Разовый платёж». Все строки — через `lang/{ru,uk,en}`, не хардкодом в blade.

**2. Дата словами, а не только цветом.** Рядом с датой — «через 16 дней» / «Завтра» / «Просрочено на 3 дня». Красный и янтарный как у `deadlineMeta` задач остаются, но текст обязателен: цвет не читается при дальтонизме, не переживает печать и не виден в письме-уведомлении.

**3. «Оплачено» — один клик и подтверждение, а не форма.** Из списка или прямо из задачи → маленькое окно: «Оплатили Hostinger Cloud Enterprise, 37 281,60 грн? [Да] [Другая сумма]». Дату не спрашивать, подставить сегодня (правку даты оставить в карточке). После — «Записал. Следующий платёж 27 июня 2027». Это самое частое действие в модуле, оно должно стоить одного клика. Рядом — «Отменить оплату» с обязательной причиной; она закрывает задачу как отменённую и переносит строку на следующий цикл (§6.5).

**4. Добавление — мастер в 4 шага, не форма на 25 полей.** Шаг 1: кто и за что (`vendor`, `product`). Шаг 2: сколько и в какой валюте, либо «сумма приходит счётом» (`amount` пуст). Шаг 3: как часто и когда следующий раз. Шаг 4: чем платим и кто платит. Всё остальное — `portal_url`, `account_ref`, `vat_note`, `notes`, `card_label` — в свёрнутый блок «Дополнительно», по умолчанию закрытый.

**5. Шаблоны вместо пустой формы.** Пресеты «Хостинг», «Домен», «Подписка на сервис», «Счёт от оператора связи»: заранее проставляют `category`, `kind`, `period_months`, `payment_method`. Остаётся вписать название и сумму. В инвентаре §5 восемь доменов и шесть хостингов — шаблон снимает половину ввода.

**6. Пояснения под полем, а не в тултипе.** Под «Кто платит» — *«ему придёт задача “пойти оплатить”»*. Под «Кто отвечает за сервис» — *«к нему идти, если сервис отвалился»*. Эти два поля путают гарантированно, а цена ошибки — напоминание уходит не туда.

**7. Автозадача самодостаточна.** Человек живёт в задачах, а не во вкладке «Оплаты». В описании задачи — всё, чтобы заплатить, не открывая биллинг: сумма и валюта, ссылка в кабинет (`portal_url`), договор или л/с (`account_ref`), способ («карта Приват •••• 1234»), и действие «Оплачено» прямо из задачи.

**8. Ничего не удаляем — кнопка «Больше не платим».** Вместо delete строка уходит в архив с датой и причиной (`archived_at`, `archive_reason`), история платежей цела. Рядом «Пауза до …» (`paused_until`) для сезонных. Неуверенный пользователь боится удалить нужное и потому не трогает ничего — ему нужна безопасная кнопка.

**9. Пустые и сломанные состояния объясняют, что делать.** Пустой список — «Пока ничего не добавлено. Начните с доменов и хостинга — их обычно 3–5», а не пустая таблица. Строка без плательщика — не тихо пропущена кроном, а жёлтая плашка «Плательщик не назначен, напоминание не придёт → Назначить». То же для строк без даты, для «у плательщика не указан отдел» (§6.1), для «карта выбрана, но не указаны 4 цифры» и для «нужен ответственный за сервис» (у отдела нет руководителя). Черновик с незаполненной картой сохранять **можно** — иначе человек бросит ввод на полпути; напоминания по такой строке работают, в списке она с плашкой.

**10. Показывать, как система поняла сумму.** Принимать `37281,60`, `37 281,60`, `37.281,60`, но под полем сразу писать: «37 281,60 грн в год ≈ 3 107 грн в месяц». Одна строка обратной связи ловит почти все опечатки — включая те, что уже есть в таблице: 980 EUR вместо 980 грн (§5.4 п.5) и дата `30.08.0226` (§5.4 п.10).

Если делать не всё сразу, порядок по отдаче: **3, 7, 9** — самое частое действие в один клик, самодостаточная задача и внятные подсказки вместо тишины.

## 8. Как встроить в код (когда будет апрув)

Ориентиры, не тикеты:

- Permission + переводы `lang/{ru,uk,en}/permission.php`.  
- Миграции `billing_items` (`kind` + `period_months`, `state` + `paused_until` + `archived_at`, `owner_label`), `billing_payments` (`type` = `paid` / `skipped` + причина).  
- Сидер: категория задач «Оплаты» и технический пользователь «Оплаты» (`system_type=admin`, уведомления выключены).  
- Policy + middleware.  
- Volt: `pages/billing/index.blade.php`, `show`, `create`/`edit` (мастер в 4 шага, §6.7 п.4) + пресеты шаблонов (§6.7 п.5).  
- Архив вместо удаления: `archived_at`, `archive_reason`, `paused_until`; в списке — «Больше не платим» и «Пауза до …».  
- Человекочитаемые периоды и даты — только через `lang/{ru,uk,en}/billing.php`, без хардкода в blade (§6.7 п.1–2).  
- Пункт в `navigation.blade.php` (desktop + mobile), `@can` / `hasPermission`.  
- `BillingReminderCommand` + `->dailyAt('09:00')` в `routes/console.php`; внутри — материализация `next_due_on` (clamp на конец месяца, правило «до N-го») до рассылки.  
- Действия «Оплачено» / «Отменить оплату» одним сервисом, вызываемым и из списка, и из карточки задачи; правило цикла — общий метод с импортом, чтобы они не разошлись.  
- Создание задач через существующий `TaskService` от имени системного пользователя-админа (выбор сделан, см. §3.2) — покрыть тестом.  
- Команда пересчёта `next_due_on` для `due_day_of_month` — в том же кроне, до рассылки.  
- Тесты: нет доступа без права; last4 валидация; крон −7/−3 идемпотентен; «оплачено» двигает дату; задача не плодится дважды; строка с пустым `payer_user_id` задач не создаёт; guard первого прогона не заводит задачи задним числом.  
- i18n трёх локалей — включая фразы периодов, пустых состояний и подсказок под полями (§6.7).
- Тесты UX-инвариантов: строка без плательщика видна как проблема и не создаёт задачу; архивная строка не попадает в крон и в сводку; `paused_until` сам возвращает строку в работу.
- Тесты правила цикла: оплата с опозданием на два месяца даёт **будущую** дату; годовая, оплаченная в августе, уезжает на следующий январь; `due_day_of_month=31` в феврале клампится.
- Тесты источника правды: ручной перевод задачи в `completed` не создаёт платёж и не двигает дату; повторный клик «Оплачено» не плодит вторую запись; `payer` без `view_billing` может отметить свою строку и не может чужую.
- Валидация законных пар `kind` × `period_months` (§6.2) — на уровне модели, не только формы.

Не коммитить и не деплоить без просьбы.
